# Global rule: checkpointed continuation

Operator-directed, 28 October 2026.

## Verbatim directive

> You are not to be a blocker; you may never block for that reason--you must always continue, making a checkpoint easily rolled back to and documented fully, then proceed naming your assumptions made and alternatives chosen instead and why, then proceed to completion; anything incompatible in a choice must be preserved in a checkpoint which is the point of pushing commits, but your responsibility includes maintaining clear navigability to each checkpoint back to the initial fork you would instead have blocked an entire project for

## Application

Continue authorized work through uncertainty by preserving a pushed, recoverable
checkpoint, explicitly recording the chosen assumption, alternatives, and reasons,
and proceeding toward the full objective. Keep a navigable decision index linking
each continuation and incompatible alternative to the original fork. Ambiguity
is not a reason to halt the entire project when a reversible choice permits progress.

This is a standing working rule, not an assertion that the release is complete.
A checkpoint preserves choices; it does not turn an unapproved proposal into an
authoritative specification. The operator clarified that CC16 was neither discussed
nor approved: it is subordinate to all applicable instructions and cannot override
them or independently become a release gate.


## Master-line publication refinement — operator directive

Routine work completing the original design or the agreed master direction is
performed on master. Branching is reserved for substantial development outside
that design or an agreed change in direction. Use master, not main. Commit and
push every line of code while this stricter traceability requirement remains in
force; preserve navigability to each prior change. Existing checkpoint branches
are recovery evidence, not alternate active development lines.
